Macの再生音を受けて、自分で設計した処理を通してからDACへ出すアプリ、Sonir Benchを作っています。[前の記事](https://zenn.dev/nadai/articles/sonir-bench-macos-dsp-workbench)では全体の構成を書きました。この記事では、その中の長いFIRの畳み込みを掘り下げます。

結果から書きます。M6のMac miniで、998,545タップの直線位相FIRを768 kHz、f64で8時間近く回し、音途切れは0回でした。

![音途切れのカウンタとCPU負荷](/images/sonir-bench-million-tap-fir-realtime/ja-dropouts-8h.webp)
*8時間近く鳴らした後のステータスバー。音途切れの内訳は左からアンダーラン、オーバーラン、処理遅れで、すべて0です*

そのときの往復レイテンシは657.43 msでした。ただし、そのうち650.09 msはフィルタ自身の群遅延で、音を運ぶ仕組みが足している遅れは7.33 msだけです。この2つを分けて考えられるようになるまでに、何度か思い込みで遠回りをしました。

## 直接畳み込みでは1 ms分しか回らない

Benchは入ってきた音を705.6 kHz（44.1 kHz系）か768 kHz（48 kHz系）へ上げてから処理します。レートを上げるフィルタ（アップサンプラー）も、ユーザーが遷移幅やタップ数を決めて設計します。

最初に測ったのは、FIRを素直に1タップずつ掛けて足す直接畳み込みです。705.6 kHzのステレオでは、1コアで757タップが上限でした。時間長に換算すると約1 ms分にしかならず、急峻なレート変換にもルーム補正にもまったく足りません。

そこで、均一分割FFT畳み込み（uniformly partitioned overlap-save）にしました。仕組みは次のとおりです。

```text
IRを長さBのK個に分割 → 各パーティションを2B点でFFTして持っておく

Bサンプルごとに:
  入力の直近2B点をFFT → 周波数領域ディレイライン(FDL)へ積む
  Σ_k FDL[p−k] · IR_k → 逆FFT → 後半B点が有効な出力
```

1ホップ分の処理は、実装ではこうなっています（1チャンネル分。エラー処理は省いています）。

```rust
// 1. 直近 2B を FFT（forward は入力を壊すのでコピーしてから渡す）
for (dst, src) in self.time.iter_mut().zip(history) {
    *dst = T::from_bus(*src);
}
self.fft.process_with_scratch(&mut self.time, &mut self.spectrum, &mut self.fft_scratch)?;

// 2. FDL へ格納
let slot = (ch * partitions + fdl_pos) * bins;
self.fdl[slot..slot + bins].copy_from_slice(&self.spectrum);

// 3. Σ_k FDL[pos−k] · IR_k
self.acc.fill(Self::zero());
for k in 0..partitions {
    let idx = (fdl_pos + partitions - k) % partitions;
    let x = (ch * partitions + idx) * bins;
    let h = k * bins;
    T::mul_add_mono(&mut self.acc, &self.fdl[x..x + bins], &self.ir_spectra[h..h + bins]);
}

// 4. 逆 FFT
self.spectrum.copy_from_slice(&self.acc);
self.ifft.process_with_scratch(&mut self.spectrum, &mut self.time, &mut self.ifft_scratch)?;

// 5. overlap-save: 有効なのは後半 B 点。realfft は正規化しないので 1/2B
let norm = 1.0 / (2 * b) as f64;
for (dst, src) in out.iter_mut().zip(&self.time[b..]) {
    *dst = src.to_bus() * norm;
}
```

FFTは[realfft](https://crates.io/crates/realfft)を使っています。時間がかかるのは3の積和で、パーティションの数Kだけ周波数ビンの数（B + 1）の複素数の積和を繰り返します。`mul_add_mono`はApple SiliconのNEONで書いていて、ステレオのときはIRのスペクトルを1回読んで左右の両方に掛けます。IRのスペクトルは100万タップで約17 MB（f64の複素数）あり、毎ホップ全部を読むので、読む回数を減らすことがそのまま速さに効きます。

1サンプルあたりのコストは、おおよそ`12·N/B`（Nはタップ数）です。タップ数に比例しますが、パーティション長Bで割られます。Apple M1で、705.6 kHz、ステレオ、1コアに対するCPU消費率を測ると次のようになりました。

| タップ数 \ B | 1,024 | 4,096 | 16,384 | 65,536 |
|---:|---:|---:|---:|---:|
| 65,537 | 21.6% | 7.6% | 3.7% | 2.4% |
| 300,001 | 38.2% | 10.9% | 4.3% | 2.7% |
| 1,048,576 | 154.5% | 33.9% | 9.5% | 4.0% |

同じ100万タップでも、B = 1,024では1コアに収まらず、B = 65,536なら4%です。効いているのはタップ数よりもBのほうです。

## 分割しても遅延は増やさない

分割畳み込みの教科書には「遅延はB」と書いてあります。これは、ホスト（プラグインを呼ぶ側）のブロック長がBより短い前提の話です。プラグインのブロック長は64〜512サンプル程度が普通なので、効率のためにBを大きく取ると、Bに達するまで入力を溜めておく必要があります。その溜めた分が遅延になります。

ホストのブロック長がBの倍数なら、溜める必要がありません。受け取ったブロックをその場で畳み込み、同じ長さのブロックとして返せます。

Benchの内部のブロック長は「入口のブロック長 × 補間比」です。入口で48 kHzの256フレームを受けると、16倍して768 kHzの4,096フレームになります。そこでBを内部のブロック長そのものに合わせました。これで、畳み込み処理が追加する遅延はゼロになります。

Bは内部のブロック長から決めます。ブロック長を割り切る最大の2の冪を取ります。

```rust
pub fn partition_for(block: usize) -> Option<usize> {
    if block == 0 {
        return None;
    }
    // ブロック長を割り切る最大の 2 の冪（= 最下位の立っているビット）。
    // ブロックが 2 の冪ならブロック長そのもの
    let b = block & block.wrapping_neg();
    (b >= MIN_PARTITION).then_some(b)
}
```

`block & block.wrapping_neg()`は、2の補数で最下位の立っているビットだけを残す書き方です。4,096なら4,096、6,144なら2,048になります。

これはテストで固定しています。素通し（単位インパルス）のIRを積んだ経路の遅延が、何も積まない経路と完全に一致することを確かめるテストです。

```rust
#[test]
fn a_default_partition_convolver_adds_no_latency_to_the_chain() {
    let empty = Chain::build(&spec_48(256), Vec::new(), config()).unwrap();
    let baseline = empty.report().latency_base_frames;

    // 単位インパルス = 素通しの IR。遅延だけを見る
    let mut ir = vec![0.0; DEFAULT_PARTITION * 128];
    ir[0] = 1.0;
    let conv = FirConvolver::new(ir, DEFAULT_PARTITION).unwrap();
    let chain = Chain::build(&spec_48(256), vec![Box::new(conv)], config()).unwrap();

    assert_eq!(chain.report().node_report.latency_frames(), 0);
    assert_eq!(
        chain.report().latency_base_frames,
        baseline,
        "畳み込みを積んだら経路遅延が増えた"
    );
}
```

申告した遅延が0であることと、実際に0であることは別の話です。そのため、同じIRを挟んだ経路に正弦波を流し、出力が申告どおりの遅延で入力と重なることも、別のテストで確かめています。

ただし、遅延が消えたわけではありません。Bを大きくすれば入口のブロックも大きくなるので、往復の遅延はBの分だけ伸びます。Bは「遅延とCPUの交換レート」です。Benchでは、Bを画面で選べるようにしています（4,096〜65,536）。

## 壊れ方1: 差し替えた直後の1.37秒間、正しい音が出ない

Benchでは、鳴らしたまま処理を差し替えられます。AとBの2つの処理を組んでおき、5〜10 msのクロスフェードで切り替えて聴き比べるためです。

最初の実装では、差し替えるたびに新しい畳み込みを空の状態から始めていました。分割畳み込みは過去のK個のブロックのスペクトルをFDLに持っているので、空から始めるとFDLが埋まるまで正しい出力が得られません。長いIRでは、その時間が最大1.37秒になりました。10 msのクロスフェードでは隠せません。

ここで気づいたのは、FDLに入っているのは入力のスペクトルであって、IRには依存しないということです。古い畳み込みのFDLをそのまま新しい畳み込みへ引き継げば、差し替えた直後から正しい出力が得られます。これを`transfer_history`として実装しました。

```rust
pub fn transfer_history(&mut self, previous: &Self) -> bool {
    if self.partition != previous.partition
        || self.channels != previous.channels
        || self.bins != previous.bins
        || self.precision != previous.precision
        // ...
    {
        return false;
    }
    // 入力側の状態はそのまま持ってこられる
    self.history.copy_from_slice(&previous.history);
    self.stage.copy_from_slice(&previous.stage);
    self.fill = previous.fill;

    // FDL は「新しいホップから順に」詰め替える。K が違うので位置は付け替える
    // （精度が違えば FDL の型が違うので、上のガードで既に落ちている）
    let geo = self.geometry();
    let (channels, previous_partitions, previous_pos) =
        (self.channels, previous.partitions, previous.fdl_pos);
    let (Some(next), Some(old)) = (self.freq.as_mut(), previous.freq.as_ref()) else {
        return false;
    };
    match (next, old) {
        (FreqDomain::F64(next), FreqDomain::F64(old)) => {
            next.transfer_fdl(old, geo, channels, previous_partitions, previous_pos);
        }
        (FreqDomain::F32(next), FreqDomain::F32(old)) => {
            next.transfer_fdl(old, geo, channels, previous_partitions, previous_pos);
        }
        _ => return false,
    }

    // 出力側は引き継がない。旧グラフが同じブロックを吐き続けているので、
    // ここで溜まっている音を持ってくると同じ音が二重に出る
    self.pending.fill(0.0);
    // ...
}
```

タップ数が変わればパーティションの数Kも変わりますが、FDLは新しいホップから順に詰め替えれば済みます。Kが増えたときは古い側が足りずにゼロのままになり、新しいIRの裾の寄与だけが数ホップ分欠けます。全体がゼロから始まるのとは桁が違うので、これは許しています。

もう1つの注意は出力側です。クロスフェードの間は古い処理も同じブロックを出し続けているので、古い処理の出力の溜まりまで引き継ぐと、同じ音が二重に出ます。引き継ぐのは入力側だけです。

移せるのは、Bとチャンネル数と精度が同じときだけです。逆に言うと、差し替えで変わりうるもの（タップ数など）からBや実装を決めてはいけない、ということになります。この原則を、このあと2回も破ることになります。

もう1つ、クロスフェードは長いほど安全というわけではありません。クロスフェードの間は新旧2つの処理を同時に回すため、CPU負荷が倍になります。クロスフェードを長くするほど、その負荷が続く時間も伸びてしまいます。そのためクロスフェードは5〜10 msに絞っています。

## 壊れ方2: 30万タップで「ぷつっぷつっ」

あるとき、30万タップのレート変換フィルタを設計して適用すると、「ぷつっぷつっ」という音しか出なくなりました。設計時の検証ロジックは「処理可能」と判定していました。

調べると、レート変換の段だけが分割FFT畳み込みではなく、直接の多相分解（polyphase）で回っていました。多相分解は補間比の分だけ計算が減るので、16倍なら1/16で済みます。それで十分に計算コストが低いと思い込んでいました。ただ、比べる相手を間違えていました。FFT畳み込みとは計算量のオーダーが違うため（`O(N)`と`O(N/B)`）、1/16にしたところで桁違いに負けてしまいます。30万タップ、ステレオ、44.1 kHz入力の条件では1コアの約35倍もの負荷となり、毎ブロックまったく間に合っていませんでした。

解決策は、畳み込みエンジンを1つに統一することでした。グラフのFIRノードもレート変換の段も、同じ分割畳み込みを使うように改修しました。

最初は、短いフィルタでは直接、長いフィルタではFFT、とタップ数で実装を切り替える形で書きました。ところがテストしてみると、差し替え時にタップ数が境目をまたぐと内部実装が変わってしまい、`transfer_history`が成立せずに引き継ぎを拒否されることが分かりました。これでは、設計を少し変えただけで音が途切れてしまいます。結局、既定の1,345タップでもFFTのほうが計算コストが低かったので、切り替えそのものをやめました。

## 壊れ方3: 上限を決めていたのはCPUではなかった

次は、「M1 Airでは30万タップが実時間の上限に見える。計算量を見積もると機械の能力より2桁小さいので、演算能力以外の原因を疑いたい」という調査でした。

サーマルスロットリング、Eコアへの割り当て、実時間スレッドでのメモリ確保、メモリ帯域を順に疑い、すべて違いました。クロックが熱で落ちないのは、8コアのうち1コアしか使っていなかったからでした。

原因はコードの1行でした。

```rust
// Bを決める関数（当時）
DEFAULT_PARTITION.min(block)
```

内部のブロック長をいくら伸ばしても、Bは4,096から動きませんでした。この上限は、往復20 msのレイテンシ予算から決めた値です。ところが、その予算の根拠はすでに消えていました（次の節）。前提が崩れたにもかかわらず、その前提に基づいて決めた値を見直すことが抜け落ちていたのです。

Bは内部のブロック長に追従させ、上限を外しました。すると、その隣に潜んでいた別の落とし穴が口を開けました。Bがブロック長より長いと、畳み込みが1回も回らないまま出力バッファを無音で埋めてしまい、何のエラーも出しません。処理経路のどこにも異常が見当たらないまま、無音だけが流れてしまいます。そこで、Bはデバイスが実際に要求してくるブロック長から決定するように改め、要求長に満たず処理できなかったブロックは数えて画面に出すようにしました。

数えるために、畳み込みの`process`は「実際に畳み込みの結果を書いたフレーム数」を返すように変えました。

```rust
/// 返すのは実際に畳み込みの結果を書いたフレーム数。残りは無音で埋める。
pub fn process(&mut self, input: &[f64], output: &mut [f64]) -> usize {
    // ...
    // 1. 入力を溜める。B たまるたびに1ホップ回す
    let mut done = 0usize;
    while done < frames {
        let take = (b - self.fill).min(frames - done);
        // ...（stage へ写す）
        self.fill += take;
        done += take;
        if self.fill == b {
            self.hop();
            self.fill = 0;
        }
    }

    // 2. 出力を吐く。足りなければ無音
    let emit = frames.min(self.available);
    // ...（pending から output へ写し、残りは 0.0 で埋める）
    self.available -= emit;
    emit
}
```

ブロック長とBが一致していれば、1回の呼び出しでちょうど1ホップ回り、受け取った分をそのまま返せます。これが前の節の「遅延ゼロ」の正体です。Bがブロック長より長いと、Bが溜まるまでの呼び出しでは`hop`が回らず、`emit`は0になります。出力の長さ自体は正しいので、返り値を見なければ誰も気づきません。

## 遅れの本体はフィルタだった

ここからが、この記事でいちばん書きたかったことです。

Benchの往復レイテンシの目安は20 msです。ブラウザの動画やゲームの音も通るので、リップシンクを考えるとこのあたりが上限になります。最初は、これを超える設計は保存させないようにしていました。

ところが、直線位相のFIRには、タップ数Nに対して`(N−1)/2`サンプルの群遅延が必ずあります。30万タップなら群遅延だけで212 msで、予算の10倍です。分割畳み込みが遅延を足さないようにしても、フィルタ自身がそれを桁違いに上回る遅れを持っていました。

実機の画面で見ると、その差は一目瞭然です。これは50万タップで設計したアップサンプラーを、48 kHz入口で組んだときの例です。

![50万タップのときの往復レイテンシ](/images/sonir-bench-million-tap-fir-realtime/ja-latency-500k.webp)
*48 kHz → 768 kHz。アップサンプラーは544,673タップ（同じ遷移幅を768 kHzで作ると、705.6 kHzより8.8%多くタップが要ります）*

アップサンプラーの354.60 msは、(544,673 − 1) / 2 = 272,336サンプルを768 kHzで割った値です。それ以外は入力5.33 ms、プロセス間通信1.00 ms、DAC 1.00 msで、合わせて7.33 msです。DACへは768 kHzのまま出しているので、レートを下げる段（デシメータ）は無く、0.00 msです。

544,673という半端なタップ数には理由があります。群遅延の272,336サンプルは、補間比16のちょうど17,021倍です。群遅延が補間比の倍数でないと、入口のレートで数えた遅れが半端なサンプル数になり、レイテンシを整数フレームで申告できなくなります。そこで、直線位相のときはタップ数を少しだけ増やして揃えています。

```rust
/// 直線位相のタップ数を変換比へ揃える。群遅延 `(N−1)/2` が低いほうのレートで
/// 整数フレームになるまで増やす
fn align_taps(requested: usize, phase: FirPhase, factor: usize) -> Option<(usize, u32)> {
    match phase {
        FirPhase::Linear => {
            let aligned = ((requested - 1) / 2).div_ceil(factor) * factor;
            let taps = aligned * 2 + 1;
            (taps <= MAX_TAPS).then(|| (taps, u32::try_from(aligned).unwrap_or(u32::MAX)))
        }
        FirPhase::Minimum => Some((requested, 0)),
    }
}
```

増やした分はゼロで埋めず、窓の中に入れて設計し直します。同じCPUを払うなら、フィルタの性能に使ったほうが得だからです。最小位相のフィルタは群遅延が`(N−1)/2`ではないので、揃える理由そのものがありません。

次に、タップ数を約2倍にしてみます。96 kHz入口で、アップサンプラーを998,545タップ、ノード列を18段にしました。

アップサンプラー単体の遅延は650.09 ms（499,272サンプル）になりました。合計は657.43 msです。入力・通信・DACの7.33 msは変わりません。96 kHz入口では補間比が8倍なので、入口のブロックは512フレームになりますが、時間にすると同じ5.33 msです。ノード列は18段ありますが、遅延は0.00 msのままです。

タップ数を倍にすると、フィルタの遅れはほぼ倍になり、運ぶ遅れは変わりません。

## 遅れを断るのをやめた

直線位相の群遅延は、全帯域で一定の、純粋な遅れです。音そのものは1ビットも変わりません。困るのはリップシンクと、一時停止や曲送りの反応（遅れの分だけ、管の中に音が残ります）の2つで、どちらもその代償を支払うかどうかはユーザー自身が決めてよい性質のものです。

そこで、遅延の予算を超える設計を一律に弾くのをやめました。代わりに、掛かっている往復レイテンシを画面に常に出すようにしています。50万タップのところで載せたのがその画面です。メーターのバーを20 msで振り切らせるのではなく、実際の値まで伸ばした上で、目安となる20 msの位置に線を残しています。「ユーザーが知らずに使ってしまう状態」を作らないことが前提であり、この可視化があって初めて成り立つ判断です。

CPU負荷も同じ扱いにしました。一度は、CPUが足りないと見込まれる設計を弾くチェックの門を設けました。しかし、事前の負荷見積もりは熱の状態だけで1.75倍も変動します。そのため、門を通過した設計であっても実時間処理が間に合う保証は最初からありませんでした。門で弾いてしまうと、かえって「門を通ったから絶対に大丈夫だ」と誤解させてしまいます。そこで門を置くのをやめ、「予報」の形に改めました。設計の時点で見込みの消費率を提示し、実際に鳴らした後は実測値と音途切れの回数をそのまま出すようにしています。

## CPUの数字は2つある

冒頭のステータスバーには、「CPU負荷46% 最大77%」と「CPU 46%」の2つが出ています。

最初は1つでした。コールバックにかかった時間を壁時計（実経過時間）で測り、ブロックの締め切り時間で割った値でした。ところが、同じ設計のまま入口のブロック長を256から512にするだけで、7.0%から22.2%へ跳ねました。音途切れは0のままで、事前の見積もりはほとんど動きません。跳ね方が連続ではなく段差だったので、長いコールバックがスケジューラの割り当て時間をまたぎ、待たされた時間まで数えているのだろうと考えました。

そこで、スレッドが自分で使ったCPU時間を別に測るようにしました。Rustの標準ライブラリにはスレッドのCPU時間を返すAPIが無いので、`clock_gettime`を1行だけ`unsafe`で呼んでいます。

```rust
/// 呼び出しスレッドがこれまでに使った CPU 時間。
pub fn thread_cpu_time() -> Option<Duration> {
    let mut ts = libc::timespec { tv_sec: 0, tv_nsec: 0 };
    // SAFETY: `ts` は有効な `timespec` で、`clock_gettime` はそこへ書くだけ。
    let ok = unsafe { libc::clock_gettime(libc::CLOCK_THREAD_CPUTIME_ID, &raw mut ts) } == 0;
    // ...
}
```

1回の呼び出しは約154 nsで、1ブロックに2回呼びます。44.1 kHzの256フレームの締め切り（5.8 ms）に対して0.005%なので、測ることで測る対象を動かしません。

測り直すと、壁時計とCPU時間は、どのBでも差が0.1ポイント以下で一致しました。跳ねは待たされた時間ではなく、本当に計算量が増えていたのです。疑っていた説明のほうが外れました。見積もりとのずれの原因は、まだ切り分けていません。

それでも、2つに分けたことには意味がありました。「一致している」と言えるようになったのは、別々に測ったからです。1つに畳んだままでは、「たぶん待たされている」から先へ進めませんでした。いまは2つを並べて出しています。

- **CPU負荷**（壁時計 ÷ 締め切り）: 処理が間に合っているかを見る数字です。待たされた時間も含まれます。100%に達すると音が途切れます。
- **CPU**（スレッドのCPU時間 ÷ 締め切り）: 純粋に演算に使った時間だけです。事前の予報が合っているかを確かめるのに使います。

8時間近く鳴らしている間の負荷の最大は77%でした。ピークでも締め切りまで2割ほどの余裕が残っていたことになります。

ただし、このときのレート変換は入口の1段だけです。DACへ768 kHzのまま出しているので、出口でレートを下げる段がありません。192 kHzまでしか受けないDACにつなぐと、出口にもう1段フィルタが加わり、その分のCPUを払うことになります。

この数字は、畳み込みをf64で回したときのものです。Benchには畳み込みの中だけをf32にするモードもあり、同じ設計で約2倍速くなります。誤差は-141 dBFSほどです。ただし、精度を変えるとFDLの型が変わって`transfer_history`による引き継ぎが成り立たないため、再生中にシームレスに切り替えることはできません。

## まとめ

- 直接畳み込みは705.6 kHzのステレオで757タップが上限です。分割FFT畳み込みにすると、100万タップが実時間で処理できるようになります。
- 内部のブロック長とパーティション長Bをそろえれば、分割畳み込みは遅延を1サンプルも足しません。その代わり、Bを大きくすると入口のブロック長も長くなります。
- 差し替えで変わりうるもの（タップ数など）から、Bや実装を決めてはいけません。FDLを引き継げなくなり、設計を少し変えただけで音が途切れてしまいます。
- 往復の遅れのほとんどは、音を運ぶ仕組みではなくフィルタ自身の群遅延です。100万タップの直線位相なら650 msで、運ぶ遅れの7 msとは桁違いです。
- 遅れの長さもCPU負荷も、システム側で一律に弾くのではなく、画面に出すことにしました。遅れは各区間の申告値の合計、CPU負荷は実測値です。

## まだできていないこと

- 往復レイテンシの値は、各区間が申告した値の合計です。群遅延は計算式どおりですが、実機ループバック録音で実測した値ではありません。また、プロセス間通信の1.00 msは見込みの固定値ですが、音声ストリーム自体のプロセス間通信は実際には発生しないため、実体のないマージン項目が内訳に残っています。
- 畳み込みは1コアだけで回しています。この処理は計算よりメモリの読み書きで頭打ちになるので、コアを増やしても線形には速くなりません。先に周波数領域だけをf32にして（2.05倍）、並列化は後に回しています。
- 低遅延と長いタップ数を両立するなら、不均一分割（non-uniform partitioned）が必要です。まだ実装していません。
