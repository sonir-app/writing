Macで鳴っている音を全部受け取って、自分で設計した処理を通してからDACへ出すデスクトップアプリ、Sonir Benchを作りました。2026年10月にベータを公開しています。

この記事では、何を作ったのか、なぜそういう形にしたのかを、全体の構成に沿って書きます。個々の部品（長いFIRの畳み込み、仮想オーディオデバイス、実時間スレッドの書き方など）は、このあと1本ずつ別の記事で掘り下げます。

## 何を作ったか

Sonir Benchは、macOSに仮想オーディオデバイスとして入ります。出力先を「Sonir Bench」にすると、Spotify、Apple Music、Qobuz、ブラウザ、ゲームなど、どのアプリの音もBenchに届きます。Benchはそれを705.6 kHzか768 kHzまで上げてから、ユーザーが組んだ処理を通し、DACが受けられるレートに戻して出します。

作ったものは3つの部品に分かれています。

- **仮想オーディオデバイス**: Cで書いたAudioServerPlugIn。coreaudiodの中で動きます
- **daemon**: Rustで書いた、画面を持たないプロセス。音の処理とデバイスの入出力はすべてここです
- **UI**: Tauri 2とReact 19。daemonとは別のプロセスです

![全体の構成](/images/sonir-bench-macos-dsp-workbench/overview.png)

## なぜ作ったか

オーディオの再生ソフトには、高品質なフィルタを何十種類も持つものがあります。ただ、多くは用意されたフィルタから選ぶ形で、自分で設計することはできません。逆に、フィルタを設計する道具はあっても、設計したものを自分の再生環境ですぐ聴き比べることはできません。書き出して、読み込ませて、再生し直す間に、さっきの音の記憶は薄れてしまいます。

窓関数付きのsincを自分で書ける人は少なくありません。困るのは書いた後で、次の3つができないことです。

1. 設計したフィルタのインパルス応答や群遅延を、並べて見ること
2. 自分のシステムで、すぐ切り替えて聴き比べること
3. 聴こえた違いが、測定で言うと何に当たるのかを知ること

Benchはこの「設計して、見て、聴き比べて、測る」を1か所でできるようにするための道具です。売りたいのは「良い音」ではありません。何が良い音かはユーザーが決め、Benchはそのための作業台になる、という考え方で作っています。

## 入口: 仮想デバイスを自作した

開発の初めは、既存のオープンソースの仮想オーディオデバイスで受けていました。ただ、そのライセンスはGPLv3で、製品に同梱して配ることができません。そこで、出荷する形では自作のAudioServerPlugInに置き換えました。

自作にしたことで、入口の振る舞いを自分で決められるようになりました。

- **対応するレートの一覧を自分で決める。** 44.1 kHz系と48 kHz系を192 kHzまで宣言しています。送出アプリが自分のレートで鳴らせれば、OSがその手前でレートを変換（SRC）しません
- **音量の操作を持たせない。** デバイスは常に等倍です。OSの音量スライダーが入口の音に効く経路そのものが無くなります
- **音のためのプロセス間通信を作らない。** プラグインは受けた出力をそのまま入力側へ折り返し、daemonはそれを普通の入力デバイスとして開きます。音の通り道は1本だけです

実際にやってみると、画面を見る限りは正常なのに、音は変わっている、という壊れ方がいくつもありました。

たとえば、デバイスの今のレートとは違うレートでストリームを開くと、OSが黙ってSRCを挟みます。エラーは出ません。そこでdaemonは、開く前にデバイスの公称レートを直接読み、そのレートで開くようにしました。CIにも、要求したレートからそのまま開くコードが無いかを調べる検査を入れています。

もう1つは、macOSが仮想デバイスからの入力もマイクとして扱うことです。マイクの権限が無いと、CoreAudioはエラーではなく無音を返します。無音のままでは原因が分からないので、権限の状態を読んで画面に出すようにしました。

## 入口が素通しかを測る

ロスレス配信を選んでいても、送出アプリが音をそのまま渡しているとは限りません。実際に測ってみると、ロスレス設定のSpotifyはビット単位で一致しませんでした。同じ日に測ったQobuzは、CD音質でもハイレゾでも完全に一致しました。

なので、Benchが「ビットパーフェクトです」と言い切ることはしません。入口に届いた音を測り、その結果を出します。測り方は2つあります。

**1つ目は入口検証です。** 決まった信号を送出アプリで再生してもらい、入口でビット単位で照合します。信号は、頭出し用のチャープ、16bitの全コード（65,536通り）を1つ残らず通すランプ、疑似乱数列、末尾の別帯域のチャープでできています。一致すれば、レート変換も、音量も、ミキサーも入っていないと確定できます。一致しなかったときは、一定倍率なら音量、伸縮していればSRC、というように原因の候補まで分けて出します。ただし、今のところこれはCLIだけで、画面にはまだ出ていません。

**2つ目は常時監視です。** 入力のコールバックで、通り過ぎるサンプルを1つずつ数えます。整数のPCMを素通ししていれば、サンプルの値は決まった格子の上にだけ乗ります。音量が掛かると格子が1段細かくなり、フィルタやSRCが入るとどの格子にも乗らなくなります。これを1秒ごとに集計して判定します。

ここで気をつけたのは、無音のときの扱いです。無音はどの格子にも乗るので、そのまま判定すると「素通しです」と出てしまいます。サンプルが足りない間は、判定そのものを出さないようにしました。

## なぜ705.6 kHz / 768 kHzで処理するのか

内部のレートを高く取る理由は、数字を大きくしたいからではありません。ユーザーが素朴な非線形処理を書いても、成り立つようにするためです。

`tanh`で歪みを作ると、倍音は上へどこまでも伸びます。48 kHzで処理すると、24 kHzより上の倍音はすぐ折り返して、可聴帯域に戻ってきます。音楽制作向けのプラグインが内部で8〜32倍のオーバーサンプリングをするのはこのためで、そのためのフィルタも書かなければいけません。

705.6 kHzで処理すれば、ナイキスト周波数は352.8 kHzです。1 kHzの音なら350次の倍音まで折り返しません。オーバーサンプリング用のフィルタも要らないので、そのフィルタが持ち込む位相のずれやリンギングもありません。`tanh`を1行書いただけでも、ここでは折り返しが起きません。

内部のレートと、DACへ出すレートは分けています。192 kHzまでしか受けないDACでも、内部では705.6 kHzで処理し、最後に1回だけ落とします。折り返しは内部で起きないので、高いレートで処理する利点はそのまま残ります。

演算はf64です。f32の丸め誤差の床がおよそ-145 dB、f64がおよそ-320 dBで、最良のDACでもノイズフロアは-130 dB前後です。これより上の精度を売りにすることはしません。

## 長いFIRを実時間で回す

Benchでは、レート変換のフィルタもユーザーが設計します。カットオフ、遷移幅、タップ数を決めると、その設計がそのまま実時間で動きます。

長いFIRを直接畳み込むと、705.6 kHzのステレオでは1コアあたり757タップで頭打ちになりました。時間にすると1 msほどで、レート変換にもルーム補正にも足りません。そこで、uniformly partitionedのFFT畳み込み（overlap-save）にしました。Apple M1で計測すると、1,048,576タップの畳み込み1本が1コアの約36〜50%で回ります。

普通、パーティションに分けて畳み込むと、パーティション長Bの分だけ遅延が増えます。Benchでは、内部の処理ブロックの長さをちょうどBにそろえました。受け取ったブロックをその場で畳み込んで、同じブロックとして返せるので、畳み込みによる遅延は増えません。タップ数を増やしても、遅延は変わらないということです。

ただ、ブロックの長さは往復の遅延に直接効きます。B = 4,096なら往復の遅延は48 kHz系で8.33 ms、44.1 kHz系で9.71 msです。今の既定はレート変換のCPU負荷を下げるためにB = 16,384にしていて、計算上は往復で約24〜27 msになります。どちらを取るかはユーザーが選べるようにして、今掛かっている遅延を画面に常に出しています。

## 鳴らす前に検算する

自分で組んだ処理は、間違えれば耳やスピーカーを傷めます。発散するフィルタも、直流を出す処理も、超音波を大きく持ち上げる設計も書けてしまいます。そこで、組んだ処理は鳴らす前に必ず3段の検査を通します。

1. **validate**: 形、値の範囲、係数が有限か、ピークの利得、25 kHzより上を持ち上げていないか
2. **simulate**: 非線形の処理を含むときだけ、正弦波、対数スイープ、帯域制限ノイズを実際に通して、NaNやピーク、直流、超音波の割合を測ります
3. **arm**: 非線形を含む処理には、最後のリミッターとソフトスタートを必ず付けます

どこかで落ちたら、その処理は鳴らさずに素通しに戻します。

線形の処理にsimulateが要らないのは、線形のフィルタは入力に無い周波数を作れないからです。超音波がどれだけ出るかは、係数から振幅特性を1回計算すれば分かります。非線形の処理は入力に無い周波数を作るので、実際に通してみないと分かりません。

処理の中身はJSONです。仕様は[sonir.app/spec](https://sonir.app/spec/)で公開していて、AIに読ませて書かせることもできます。ただ、AIがdaemonを直接操作する経路は作っていません。AIが書いたJSONは人が受け取ってBenchに渡し、検査に落ちたら、その結果を人がAIに貼り戻します。会話の流れで、知らないうちに出音が変わることが無いようにするためです。

## 聴き比べる

処理はAとBの2つを同時に組んでおき、切り替えて聴き比べます。切り替えは5〜10 msのクロスフェードで、音は途切れません。

聴き比べでは、音量が少し大きいほうが良く聴こえます。なので音量合わせを既定で入れていて、何dB動かしたかを画面に常に出します。音量合わせの値は、鳴っている音を測って決めるのではなく、処理の係数から計算します。鳴っている音を測ると、曲ごとに補正が変わり、同じ聴き比べを繰り返せなくなるからです。

## 越えない線: 受けた音をファイルにしない

仮想デバイスで受けた音は、どんな形でもファイルに書き出しません。書き出せるようにすると、ストリーミング配信の音をそのまま保存する道具になってしまうからです。

これは設定でも画面の注意書きでもなく、型で守っています。音声バッファは出所を型パラメータとして持ちます。

```rust
// 出所は2つだけ。キャプチャ由来か、それ以外か
pub struct Owned;
pub struct Captured;

// ファイルへ書けるのはOwnedだけ
pub trait FileSink {
    type Sample: Sample;
    type Error;
    fn write(&mut self, audio: Audio<'_, Owned, Self::Sample>) -> Result<(), Self::Error>;
}
```

`Captured`から`Owned`へ変える手段はありません。2つの信号を混ぜると、`Captured`が一滴でも混ざった結果は`Captured`になります。「キャプチャした音をファイルに書けない」ことは、`compile_fail`のdoctestで、そう書いたコードがコンパイルに失敗することとして検査しています。

型で守れるのはプロセスの中だけです。UIとつなぐWebSocketには、波形を運ぶ欄そのものを作っていません。運ぶのはレベルやスペクトラムなどの数値だけです。位相付きのスペクトルやインパルス応答も、逆FFTで波形に戻せるので運びません。

## まだできていないこと

- ローカルファイルを再生するプレイヤーは、まだありません。今はほかのアプリの音を受ける使い方だけです
- 入口検証は、まだ画面に出ていません（CLIのみ）
- 既定の設定では、往復の遅延が目安の20 msを超えています
- macOS（Apple Silicon）だけです
- 部屋をスマートフォンで測って補正するアプリ（Sonir Remote）を作っていますが、実機で測って送る一周はまだ確かめていません
